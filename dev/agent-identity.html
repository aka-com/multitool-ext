Attested agent identity — every surface, every assurance tier

Today every agent-plane caller is named by a self-reported x-multitool-client header (daemon/mod.rs:281), and the UI says so everywhere by wrapping the name in .untrusted-identity plus a "self-reported" tooltip. This proposal adds an OS-attested identity beside that label, and re-ranks the UI so the verified name leads when there is one. Because attestation is only strong on macOS over the control socket, every surface has to degrade honestly — flip the tier switch to see all four states.

Assurance

Surface 1Traffic-confirmation sheet — the decision that matters most

The approval sheet is where an unverified name does the most damage: it is an input to a human trust decision. Today the title is Allow "{approvalAgentName(agent)}" to use … (app.tsx:5988) and the facts list carries one Agent row (app.tsx:5998), both fed by the self-reported label.

Proposal: when the OS attested the caller, the attested program name becomes the headline and loses its quotes — quotes are for strings we cannot vouch for. The verified chip lives outside the name, in chrome the label's own text cannot reproduce, and the self-reported label drops to its own Reported as row whenever it differs. When nothing was attested, the sheet keeps today's quoted-and-isolated treatment and says plainly that the name is self-reported.

Surface 2Requests banner and waiting cards — the glance surfaces

The banner names a lone request through approvalWantsLine() (approval-presentation.ts:71), and each waiting card repeats the name in its context line via shortAgent() (app.tsx:1034, card at app.tsx:1189). These are the surfaces a user reads in half a second, so they get the least room and the most benefit from a single unforgeable glyph.

Proposal: one 11px shield-check ahead of the name at verified tier, nothing at all at the lower tiers — an absent mark is the signal. No extra words: the banner line is already ellipsised at one line, so the chip must cost nothing but its glyph.

Surface 3Identity disclosure — the new chrome

This is the one genuinely new surface. It is the answer to "verified by what?", reachable from the Agent row of the approval sheet, from an activity row, and from a live session. It has to do two jobs that pull in opposite directions: show the evidence chain, and stop the user from over-reading it.

Proposal: a popover in three parts — what was attested, how (the two-link chain, each link marked pass/absent), and an explicit what this does and does not mean block. That last block is not decoration: a verified agent that has been prompt-injected is still verified, and the disclosure is the only place with room to say so.

Surface 4Activity log — rows, chips, and the agent filter

Each row carries reported as "{entry.agent}" in an .act-chip (app.tsx:4129), and the Agent filter lists those raw strings (app.tsx:4391). Because the chip text is the only record, history cannot distinguish a real Claude Code call from anything that borrowed the name — including retroactively, after you learn a key leaked.

Proposal: persist the attestation next to the label on AuditEntry and render it as the chip, so the log becomes evidence. The filter groups by attested identity, with claimed labels collected under a separate heading — that grouping is the fastest way to spot "something used codex's name from an unattested session at 03:00".

Surface 5Live sessions, elicitation, and the connect-request toast

Three smaller surfaces that name an agent. LiveSessions (app.tsx:1043) is the one place today that prints the agent name without .untrusted-identity — worth fixing regardless of this feature. The elicitation dialog leads with agentLabel() (app.tsx:5828), and the connect-request toast interpolates the name directly (app.tsx:12837).

Proposal: the same chip, sized down. In the toast the chip is the difference between "some process wants a new connection" and "Claude Code wants a new connection" — and the request quota that defends against notification flooding should key off the attested identity, not the label it chose (broker.rs:2359 debounces on (client, service) today).

Surface 6Where each tier comes from — the honest matrix

The tier is not a preference, it is whatever the operating system could actually prove on the path the caller used. The active row follows the switch above.

TierHow it arisesWhat the OS provedUI treatment
Verified macOS, control socket. Broker checks its socket peer's code signature against its own, then trusts that peer's report of its signed parent. The program is genuinely the one it claims, signed by a known team. Attested name leads, unquoted, green shield.
Identified Linux, control socket. SO_PEERCRED plus /proc/<pid>/exe; no signature to check. An executable path, defeatable by same-user ptrace. Name leads, grey chip reading "identified", no shield.
Interpreter Agent runs under node / python3 — e.g. an npm install of a harness. The runtime is signed; the agent is not. Only the runtime's identity, which says nothing about the script. Self-reported label leads (quoted); runtime shown as a secondary fact.
Claimed Hosted broker over TCP, a direct endpoint client, or any process using the shared agent key without the helper. Nothing. HOSTING.md:8 already says this. Today's treatment, made explicit: quoted, isolated, dashed "unverified" chip.

Surface 7The part that is not cosmetic — approval-window scoping

An identity feature that only changes labels is theatre. The concrete behavioural win is in approvals.rs:414: an "approve for 15 minutes" window is currently keyed by the self-reported label, so any caller that sends the same header rides the window a user opened for something else. That is a real privilege-transfer bug that attestation closes.

Proposal: key the window on the attested session when there is one, and say so on the button and in the resulting activity entry. At claimed tier the wording must get weaker than today's, not stronger — it is the same behaviour, now disclosed.

Proposed

Copy rules the mockup is enforcing

  • Quotes mean "we cannot vouch for this string." Attested names lose the quotes; claimed names keep them. That makes the punctuation itself carry meaning consistently across all seven surfaces.
  • The verified mark never sits inside attacker-controlled text. Flip the spoof switch at any tier: a label of Claude Code ✓ verified by Anthropic renders inside the quoted, BiDi-isolated slot and never acquires chrome. This is why the chip is a separate element and the attested name is a separate field, not a formatted version of the label.
  • Absence is a signal, not a gap. Lower tiers get a dashed outline chip rather than nothing, so "unverified" reads as a determination Multitool made rather than a feature that failed to load.
  • Verified is an identity claim, never a safety claim. Every disclosure states that a verified agent can still be steered by content it read. Nothing in the UI says "trusted".
  • No tier grants anything extra. Attestation only ever adds confidence to a decision the user still makes; a claimed session keeps exactly today's authority, so there is no incentive to downgrade and nothing new to attack.

Ships as a real defence

Approval-window scoping, per-identity connect-request quotas, and an audit trail that separates attested from claimed. All three work without any new authorization model.

Needs plumbing first

Peer credentials on the Unix listener: it is served with a bare axum::serve (daemon/mod.rs:841), so there is no per-connection info at all today — TCP gets ConnectInfo, the socket gets nothing.

Explicitly out of scope

This does not isolate agents from each other, and it is not authorization. A same-user process can still use the shared key directly — it simply arrives as claimed and gets its own approval prompts.
